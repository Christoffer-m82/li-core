## Bounded Calendar diagnosis

After promotion, the owner authorized one read-only Calendar diagnostic request. The one-use local
runner verified `db1d17c` at 100% traffic, authenticated readiness and schema 0.42 before recording a
durable dispatch marker. The application attempted one `calendar.search` for a one-day UTC interval
with a maximum of one result. It requested no query text, mutation approval or model call.

The operator-facing request expired while queued, but the exact request-correlation lookup proved
that the backend had processed it. The only inspected application entry contained the allowlisted
fields `action=calendar.search`, `category=authentication`, `stage=oauth` and `http_status=400`.
No event, query, provider body, URL, header, credential, personal record or unrelated historical log
was retrieved or displayed. No retry was made.

Under the deployed adapter, this exact category/stage/status combination is produced by Google's
`invalid_grant` machine code during refresh-token exchange. It establishes that the stored refresh
authorization is invalid, expired, revoked or no longer matches the OAuth client configuration; it
does not distinguish those causes further. Google's [OAuth guidance](https://developers.google.com/identity/protocols/oauth2/web-server#offline)
directs the user through authorization again when refresh returns `invalid_grant`. Repair requires a
separately authorized owner consent flow, replacement of the refresh-token secret with a new numeric
version, and deployment of a reviewed backend revision referencing it. Existing client credentials
should be retained unless the new consent flow proves they are invalid.

## Recovery and remaining gates

`li-os-release-a7601b7` remains a schema-compatible availability fallback but contains the
transport-log privacy defect corrected by `db1d17c`. It must not be described as privacy-safe or
used for Calendar/provider reads merely to prove health. If an incident makes fallback unavoidable,
record the restored risk, minimize provider activity and prepare a corrected immutable release.
Application rollback does not reverse schema 0.42.

The one authorized diagnostic read is complete and must not be repeated under the same approval.
OAuth repair is a separate protected action. After that repair is reviewed and deployed, a fresh
bounded read authorization and cost check are required before proving provider-backed Calendar
display. Physical-device/owner/stability acceptance, historical-log assessment and the action-time-
confirmed `LIOS42` archive remain outstanding. Weekly Avanza quotes and specialist recency ordering
remain planned rather than implemented.
